# Demo semantic color mapping

Status: implementation contract for the rendered demo components.

This document is the single color-mapping decision for the three implementation lanes. It is intentionally separate from the later source edits: the lane workers may replace classes only according to this contract, and they must preserve the current behavior, copy, A/B structure, and unrelated working-tree changes.

## Scope and source of truth

The rendered demo surface is the content produced by the 192 condition components under `src/components/demos/*-condition-*.tsx`. The three shared files in the same directory are also rendered or mounted by the demo flow and are listed in the lane manifest below. `src/components/pattern-demo.tsx` is an autogenerated registry and `src/lib/patterns.ts` is the thesis-backed catalog; neither is an implementation-lane file.

The project uses Tailwind CSS v4 through `postcss.config.mjs` (`@tailwindcss/postcss`). There is no `tailwind.config.*`; `components.json` has an empty Tailwind config path and declares the shadcn `base-nova`/`neutral`/CSS-variable setup. The semantic utility names come from the `@theme inline` block in `src/app/globals.css`:

- surfaces: `background`, `card`, `popover`, `muted`, `secondary`, `accent`;
- foregrounds: `foreground`, `card-foreground`, `popover-foreground`, `muted-foreground`, `secondary-foreground`, `accent-foreground`, `primary-foreground`;
- actions and status: `primary`, `secondary`, `accent`, `destructive`;
- controls and focus: `border`, `input`, `ring`.

`:root` supplies the light values and `.dark` supplies the dark values. The same semantic class therefore resolves to the correct light/dark value; do not duplicate a semantic class with a hard-coded `dark:text-*` or `dark:bg-*` palette pair.

## Mapping contract

Use the exact utility families below. Opacity modifiers such as `/10`, `/20`, `/40`, `/50`, and `/60` are allowed only on the named semantic token; they do not turn a semantic class back into a literal palette.

| Role in a rendered product surface | Replace hard-coded role/palette with | Implementation rule |
| --- | --- | --- |
| Page or primary surface | `bg-background text-foreground` | Use for the demo's main neutral canvas or a nested page-like region. |
| Card/panel surface | `bg-card text-card-foreground` | Use for cards, product panels, feeds, dialogs, and grouped content. |
| Popover/overlay panel | `bg-popover text-popover-foreground` | Use when the region is layered above the current surface. |
| Muted/inset surface | `bg-muted text-muted-foreground` or `bg-muted/40` | Use for tracks, secondary metadata blocks, inactive rows, and low-emphasis status containers. |
| Secondary/accent surface | `bg-secondary text-secondary-foreground` or `bg-accent text-accent-foreground` | Use only when the UI concept is a secondary or highlighted control—not as a substitute for a red/green A/B encoding. |
| Primary text | `text-foreground` (or inherited `text-card-foreground` inside a card) | Headings, labels, prices, and readable body copy must not use `text-red-*`, `text-green-*`, or another hue merely to create hierarchy. |
| Secondary text and metadata | `text-muted-foreground` | Use for captions, helper copy, timestamps, fine print, and explanatory metadata. Use opacity on this token when the existing hierarchy needs to stay quieter. |
| Text on a primary action | `text-primary-foreground` | Never use `text-white` on a normal primary action. |
| Text on secondary/accent action | `text-secondary-foreground` / `text-accent-foreground` | Keep the foreground paired with its surface token. |
| Structural border | `border-border` (optionally `border-border/60`) | Cards, separators, neutral rows, and layout boundaries use this token. |
| Input/control border | `border-input` | Use for text inputs, checkboxes/radios, selects, and other form-control outlines. |
| Selected/focus border | `border-ring` or `focus-visible:border-ring` | Do not encode selection/focus with a palette border. |
| Destructive border/status | `border-destructive` or `border-destructive/30` | Use only for a genuine destructive/error state, not just because a panel is Variant A. |
| Primary action | `bg-primary text-primary-foreground hover:bg-primary/80` | This is the canonical shadcn default action. It is the replacement for ordinary `bg-green-*`, `bg-red-*`, `bg-blue-*`, and other colored CTA fills. |
| Secondary action | `bg-secondary text-secondary-foreground hover:bg-secondary/80` | Use for a less prominent but still actionable control. |
| Outline action | `border-border bg-background text-foreground hover:bg-muted hover:text-foreground` | Keep the border and fill semantic; do not use white/blue palette pairs. |
| Ghost action | `text-foreground hover:bg-muted hover:text-foreground` | Use when the control has no persistent fill. |
| Link | `text-primary hover:underline` | A link's action color is primary; its visited/hover treatment must not be a literal hue. |
| Destructive/error status | `border-destructive/30 bg-destructive/10 text-destructive` with `hover:bg-destructive/20` | This is the available shadcn destructive pattern. The theme does not declare `--destructive-foreground`; do not invent `text-destructive-foreground` in a demo file. A solid destructive button should be avoided unless a separate theme-token change defines and contrast-checks its foreground. |
| Positive/neutral status | `border-border bg-muted/40 text-foreground` and `text-muted-foreground` for supporting copy | The current theme has no success or warning token. Do not fake one with `green-*`/`yellow-*`; make the state explicit in copy/iconography and keep the surface themeable. |
| Native control accent | `accent-primary` (or `accent-destructive` for a genuine destructive control) | Applies to checkbox/radio/range/progress accents. Preserve a measured hue only under the color-signal exception below. |
| Progress track/fill | `bg-muted` track and `bg-primary` fill | A progress bar is not automatically a success/error signal. If its color is part of a measured visual condition, mark/retain it as an explicit signal instead of using this default. |
| Focus ring | `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-ring/50 focus-visible:ring-offset-2 focus-visible:ring-offset-background` | For destructive controls, use `focus-visible:border-destructive focus-visible:ring-destructive/20` in addition to the common keyboard-visible treatment. Never remove the focus indicator to make a palette transition fit. |
| Disabled control | `disabled:pointer-events-none disabled:cursor-not-allowed disabled:opacity-50 disabled:bg-muted disabled:text-muted-foreground` | Disabled controls stay legible and visibly unavailable. Do not use red/green disabled fills or a hard-coded white foreground. |
| Placeholder/selection | `placeholder:text-muted-foreground selection:bg-primary selection:text-primary-foreground` | Keep native input affordances tied to the semantic control tokens. |
| Dark/scrim surface | `bg-foreground text-background`, with `bg-foreground/40` or `/60` for a scrim | This replaces `bg-black/*`, `bg-[#171717]`, and white-on-black utility pairs used for a dark simulated subpanel while remaining theme-driven. Use `bg-background text-foreground` for a normal light subpanel. |
| Semantic SVG icon | `text-primary`, `text-destructive`, `text-muted-foreground`, `fill-primary`, `fill-destructive`, `fill-muted-foreground`, `stroke-primary`, `stroke-destructive`, or `stroke-muted-foreground` | SVGs that communicate UI state follow the table. Raw artwork attributes are an exception, not a product-surface role. |

### State and dark-mode handling

1. `:root` and `.dark` are theme modes. Use one semantic class (`bg-card`, `text-muted-foreground`, `border-border`, etc.) and let the CSS variables swap values. Remove redundant hue-specific `dark:*` pairs for ordinary product UI.
2. A demo's internal `isDark`, Variant A, and Variant B values are experimental conditions, not Tailwind dark mode. They must not be implemented with `dark:`. Both panels should use the same semantic product treatment unless a thesis condition explicitly measures a visual color/hue or visual prominence difference.
3. `hover:`, `focus-visible:`, `active:`, `disabled:`, `aria-*`, and `data-*` variants apply to the semantic token: e.g. `hover:bg-muted`, `focus-visible:ring-ring/50`, `disabled:bg-muted`. Do not leave a palette variant behind in only one state.
4. Keep the distinction between product content and audit chrome. A `mode === "auditor"` block containing formulas, mechanism labels, or post-action diagnostic explanation is not part of the simulated product surface; it may retain a diagnostic treatment if that treatment helps an auditor read the result.
5. Preserve the existing `data-dp-color-signal` marker and its exact hue/styling when the source deliberately measures color, hue, or visual similarity. The marker is the explicit opt-out from the ordinary neutral product mapping; do not remove it or add it to unrelated content.

## Intentional residual exceptions

These are the only residual categories allowed after the implementation lanes edit their owned product surfaces:

1. Shared Hermes/auditor chrome. `demo-shell.tsx`, `demo-section.tsx`, and `view-mode-toggle.tsx` own the blue/white shell, audit badge, view switch, and isolate links. Their `#0000f2`, white, and audit-yellow treatments are outside `data-dp-content` and preserve the surrounding Hermes chrome. Lane 3 is the single coordination owner; do not duplicate helper edits in lanes 1 or 2.
2. Explicit thesis color signals. Keep color utilities and dynamic hues inside the `data-dp-color-signal` regions in exactly these files: `activity-messages-condition-3.tsx`, `conflicting-information-condition-2.tsx`, `disguised-ad-condition-2.tsx`, `intermediate-currency-condition-3.tsx`, `limited-time-message-condition-2.tsx`, `low-stock-condition-2.tsx`, and `plain-evil-condition-2.tsx`. These encode a measured color, hue, A/B visual similarity, or urgency spectrum; they are not generic success/error decoration.
3. Diagnostic/auditor-only explanation styling. A palette can remain on an element only when that element is rendered solely inside an auditor/diagnostic branch and communicates the audit result or formula outcome. If the same node is visible in the user-facing product fragment, use the normal mapping instead. Keep diagnostic text and formula colors out of the product panel so color cannot disclose the A/B answer.
4. Non-utility artwork. Literal SVG `fill="#..."`/`stroke="#..."` values and colors that are intrinsic to a decorative illustration or thumbnail are asset details, not Tailwind product tokens. In the current snapshot, the raw SVG artwork exceptions are `auto-play-condition-1.tsx`, `granting-and-interaction-condition-1.tsx`, `cuteness-condition-1.tsx`, `cuteness-condition-2.tsx`, and `cuteness-condition-3.tsx`. Do not rewrite artwork geometry while doing this refactor. SVG utility classes on controls/statuses remain in scope; do not classify a UI badge or progress indicator as artwork merely because it is inside an SVG.
5. Measured inline styles. Inline `hsl(...)`/`rgb(...)` used as the measured hue/contrast stimulus remain only where the source is testing that exact value (for example the low-contrast text in `drip-pricing-condition-2.tsx` and `hidden-information-condition-2.tsx`, the hue stimulus in `limited-time-message-condition-2.tsx`, and the dynamic hue in `low-stock-condition-2.tsx`). Ordinary state styling must become semantic classes.

Do not add new residual exceptions for convenience. If a palette remains after the sweep, classify it as one of the five categories above in the implementation handoff or convert it.

## Shared helper ownership

The following helper files have a single owner to avoid conflicting edits:

- Lane 3 owns coordination for `src/components/demos/demo-shell.tsx` (shell framing, A/B labels, auditor header), `src/components/demos/demo-section.tsx` (mode bar and isolated links), and `src/components/demos/view-mode-toggle.tsx` (user/auditor switch).
- These helpers are not product-surface conversion targets in this pass. Their blue/white chrome is intentionally retained; only a future compatibility change that is explicitly required by the mapping may touch them.
- `src/components/pattern-demo.tsx` remains autogenerated and is not owned by any lane. `src/lib/patterns.ts` and `src/app/globals.css` are shared sources of truth and are not to be reset or reformatted by implementation lanes. Existing unrelated working-tree changes in those files must survive.
